CML Admin Guide (operations runbook)¶

Operational procedures for CML administrators. For the pilot, firms are manually enrolled and priced. For how the system works (data model, ranking/pricing engines, integrations) see docs/system-design.md.

⚠️ Security note: all admin endpoints require the ADMIN_API_KEY (X-Admin-Key header). Treat it as a secret — never paste a real key into docs, tickets, or commits.

Contents: §1 firm-user enrolment · §2 database reseeds & Master Export refreshes · §3 testing transactional email · §4 admin metrics dashboard · §5 local development environment · §6 repository, CI gates & deployment wiring · §7 domains & DNS (apex → www).

1. Enrolling a new firm user¶

1.1 Mental model¶

A firm does not self-serve sign-up. The admin invites a firm; the firm then sets its own password from a one-time link. Three facts to keep straight:

  • Two different emails exist on a firm — they are not the same thing:
Field Lives on Set by Purpose
Organisation.referral_email the firm/org record admin / Master Export import Where the enrolment invite is sent, and where Proceed/Callback lead notifications go
FirmUser.email the user record the firm, during enrolment The firm's login credential (also used for password reset)
  • The binding is the enrolment token, not the email. The single-use token identifies the organisation; whoever opens the link becomes a login user on it. The login email the firm types is not checked against referral_email, nor against the address the invite was sent to.
  • A firm can have more than one user. Once a firm is enrolled, an additional colleague is invited with invite-user (§1.5), which mints a token for the same org and leaves referral_email alone. Each invite replaces the org's outstanding token, so only the newest link works.
  • The invite email becomes the lead address — choose it carefully. The email confirmed at invite time (CLI prompt or JSON body) overwrites referral_email on the org, and that is where all future Proceed/Callback leads go. Enrolment never syncs it back from the sign-up email, and once a firm is enrolled there is currently no admin endpoint to change it (re-invite returns 409) — only a Master Export re-import (§2.B) or direct DB access. So invite the firm's intended lead inbox (e.g. enquiries@…), not a personal address.
  • FirmUser.email is globally unique — the same email cannot be reused across two firms.

1.2 The flow at a glance¶

(admin) org exists with a referral_email
        ▼
(admin) POST .../invite-enrollment ──▶ generates single-use token, sends invite (prod) / returns token (local)
        ▼
(firm)  opens /enroll/<token> ──▶ sets login email + password, accepts terms
        ▼
(firm)  logged in at /dashboard; can log in at /login, manage pricing, reset/change password

Adding a colleague to a firm that is already enrolled follows the same shape, minus the org changes:

(admin) POST .../invite-user {"email": "colleague@firm.co.uk"} ──▶ new single-use token, invite to that address
        ▼                                                          (referral_email untouched)
(firm)  opens /enroll/<token> ──▶ sets their own login email + password, accepts terms

1.3 Prerequisites¶

  1. The admin API key. Every /api/admin/* call requires X-Admin-Key: <key>.
  2. Local dev: local-dev-admin-key (from .env / docker-compose.yml).
  3. Production: the ADMIN_API_KEY value in Railway env vars (a real secret — never commit it).
  4. The organisation must already exist, created by the Master Export import (scripts/import_master_export.py). There is no admin endpoint to create an org; a brand-new firm must be added to the export and re-imported (§2).
  5. A referral_email for the organisation. The invite endpoint refuses (HTTP 400) without one — but it can be supplied at invite time (the CLI prompts for it; the raw endpoint accepts an optional {"referral_email": ...} body), so a missing/stale email on record is not a blocker.

Base URLs: - Local API http://localhost:8000 · Local portal http://localhost:3000 - Production API https://api.choosemylawyer.ai · Production portal https://www.choosemylawyer.ai (www is the canonical host — see §7. The underlying Railway URLs still work, but prefer the custom domains: the frontend calls api.choosemylawyer.ai, and it is in the CSP connect-src.)

1.4 Step by step¶

The easy way — the cml-onboard CLI (backend/scripts/onboard_firm.py):

cml-onboard            # production (the default — sends real emails)
cml-onboard --local    # local docker, for testing

The alias sources a local (never-committed) secrets file holding CML_ADMIN_API_KEY (and optionally CML_API_URL) — then runs the script with uv. The CLI:

  1. asks for a firm-name search and lists matches with their status (name, SRA number, enrolled / not enrolled, email on record);
  2. branches on that status — a not-enrolled firm gets the enrolment prompt below; an enrolled one gets the add-a-user prompt (§1.5);
  3. asks for the referral email — Enter keeps the one on record;
  4. shows a confirmation summary (the action, firm, email, API host) and only sends on an explicit y;
  5. sends the invitation and prints the link, then offers to do another firm.

The manual way — curl. Find the organisation (optionally filter with &search=):

curl -s -H "X-Admin-Key: $ADMIN_API_KEY" \
  "$API_BASE/api/admin/organisations?enrolled=false&limit=20"

The response lists each org's id, trading_name, enrolled, referral_email. Then send the invitation — the optional body sets/overrides the org's referral_email first:

curl -s -X POST -H "X-Admin-Key: $ADMIN_API_KEY" -H "Content-Type: application/json" \
  -d '{"referral_email": "person@firm.co.uk"}' \
  "$API_BASE/api/admin/organisations/<ORG_ID>/invite-enrollment"

Success returns:

{
  "message": "Enrollment invitation sent to person@firm.co.uk",
  "enrollment_token": "<single-use-token>"
}

This generates a fresh single-use token, stamps it on the org, and emails the invite to the org's referral_email. The enrolment URL is <portal-base>/enroll/<enrollment_token>.

  • Production: SparkPost sends the email; the token is also returned so you can hand-deliver the link.
  • Local dev: email runs in mock mode (logged only). Build the link from the returned token, e.g. http://localhost:3000/enroll/<single-use-token>.

The firm completes enrolment. The /enroll/<token> page captures full name, login email, password (min 8 chars), and a mandatory terms acceptance. On submit the org is marked enrolled = true, the token is marked used, and a FirmUser (role admin) is created. The token is single-use.

Confirm:

curl -s -H "X-Admin-Key: $ADMIN_API_KEY" \
  "$API_BASE/api/admin/organisations?enrolled=true&search=<firm name>"

The firm should appear with "enrolled": true. From here it self-manages (login, pricing, password).

Visibility ≠ enrolment. Being enrolled makes a firm a contactable candidate, but its Proceed/Callback buttons only appear when it ranks into the top-5 contactable, which also requires active_in_pilot = true. See docs/system-design.md §7.

1.5 Adding another user to an enrolled firm¶

When a colleague at a firm that is already enrolled needs their own login, use cml-onboard exactly as above and pick the firm — because it shows as enrolled, the CLI switches to the add-a-user prompt. It asks for the colleague's email with no default (so Enter can't invite the firm's referral inbox by accident), states that the firm's referral_email is unchanged, and warns that this replaces any outstanding invitation link for that firm.

The equivalent curl — note the field is email, not referral_email:

curl -s -X POST -H "X-Admin-Key: $ADMIN_API_KEY" -H "Content-Type: application/json" \
  -d '{"email": "colleague@firm.co.uk"}' \
  "$API_BASE/api/admin/organisations/<ORG_ID>/invite-user"

Success returns the same shape as invite-enrollment (message + enrollment_token); the colleague completes the ordinary /enroll/<token> journey and gets a FirmUser (role admin) on the same org.

Two properties worth knowing:

  • The token is not bound to the invited address. It identifies the organisation, so whoever holds the link can register under any unused email. The endpoint's up-front "email already registered" check is a courtesy — it stops you burning a token on a duplicate, not a guarantee about who signs up.
  • One outstanding invite per firm. Each invite (of either kind) overwrites the org's token, so an earlier unused link stops working. Invite one person at a time.

The endpoint refuses (409) for a firm that is not enrolled — use invite-enrollment for those.

1.6 Troubleshooting¶

Symptom Cause Fix
401 Invalid admin key Missing/wrong X-Admin-Key Use the correct key for the environment
404 Organisation not found Wrong org_id Re-check the id from the list endpoint
409 Organisation is already enrolled invite-enrollment on an enrolled firm For a locked-out firm use password reset; for an extra colleague use invite-user (§1.5)
409 Organisation is not enrolled invite-user on a firm that hasn't enrolled yet Use invite-enrollment — the first user arrives with enrolment
409 Email already registered That login email already belongs to a FirmUser (globally unique) Invite a different address
400 Organisation has no referral email on record referral_email is null and none supplied Re-invite supplying the email (CLI prompt, or the JSON body above)
"Invalid or already-used enrollment token" Token consumed, or a newer invite replaced it Send a fresh invite, use the newest link
"Email already registered" Login email already used by another firm (globally unique) Enrol with a different email

Setting a missing referral_email: supply it at invite time — the CLI always asks, and the raw endpoint accepts {"referral_email": ...}. Direct DB access is no longer needed for this.

Re-inviting an org issues a new token and invalidates the previous link — always hand over the newest link. You cannot re-run enrolment on an already-enrolled org (409); use password reset for a locked-out enrolled firm, or invite-user (§1.5) to add a colleague.

1.7 After enrolment — password lifecycle (no admin action)¶

  • Forgot password — /forgot-password: the firm receives a reset link valid 3 hours, single-use. Locally (mock email) read the token from the DB: 
    docker compose exec -T db psql -U cml -d cml_db -c \
  "SELECT email, password_reset_token, password_reset_expires_at FROM firm_users WHERE email='<login-email>';"
  • Change password — /profile (logged in): confirm current password, set a new one.

There is no admin password-reset endpoint.

2. Database reseeds & Master Export refreshes¶

⚠️ Migration policy changed at go-live (issue #155, D-4)¶

The pilot is live and holds real consumer leads. Schema changes are now made by cutting a new Alembic revision — additive and reversible. 0002 is the first such revision.

The former pre-launch policy (edit 0001_initial_schema.py in place, then drop and recreate the database) must no longer be followed: it destroys real data. §2.A below is retained only for local development databases and for a deliberate, backed-up production rebuild.

Routine schema change, local and production: 

cd backend && uv run alembic upgrade head
Confirm any new revision applies to a database already stamped at the previous head, not just to a fresh one.

There are two distinct procedures for reseeding data. Pick by whether the database schema changed.

Situation Procedure Destroys other data?
A deploy changed any table/column (schema) New Alembic revision + alembic upgrade head No
Rebuilding a local dev DB, or a deliberate backed-up production rebuild 2.A Wipe-and-reseed Yes — drops everything
Only the data changed (new firms/prices, or new JSON keys in price_cards.pricing) 2.B Import-only refresh No — preserves users/appointments/reviews/sessions

Note: adding keys inside the price_cards.pricing JSONB is not a schema change (no migration); use 2.B. Adding/removing a table or column is a schema change — cut a revision.

2.A Wipe-and-reseed (local rebuild, or backed-up production rebuild)¶

Why it exists: under the retired pre-launch policy, schema edits were made in place in 0001_initial_schema.py. An in-place edit no-ops on an already-migrated DB (Alembic sees the revision as applied), so the live schema went stale and the app 500s on first touch (often looking like CORS), and the only fix was to drop and rebuild.

⚠️ Drops every row — firms, firm users, chat sessions, appointments, reviews. Do not run this against production to apply a schema change — cut a revision instead. If you must rebuild production deliberately, take a pg_dump first.

railway link
railway status          # confirm Project + Environment are production
scripts/wipe-and-reseed-railway-db.sh --dry-run   # preview, touches nothing
scripts/wipe-and-reseed-railway-db.sh             # type WIPE to proceed

The script drops the public schema, runs alembic upgrade head, then imports the Master Export. Requires railway, psql, jq, uv, and public networking on the Postgres service.

Geocoding matters. Offices with NULL lat/lng are silently excluded from distance scoring. The bundled script geocodes by default, so offices get lat/lng automatically; only if you deliberately run the import with --no-geocode should you follow it with a geocoded import (§2.B step 2) so the Distance factor can score.

2.B Import-only refresh (data only, no schema change)¶

The importer is idempotent: organisations are upserted by cml_firm_id; offices, price_cards, complaints_summary, regulatory_summary are deleted and re-inserted. All other tables are untouched.

⚠️ Not valid when an export renumbers CML firm IDs (e.g. a firm is removed and the IDs above it shift down, as in the 16.07.26 export). The cml_firm_id upsert then tries to give an existing row another firm's SRA number and collides on the organisations_sra_number_key unique constraint. Such exports need the full rebuild path: 2.A in production, or locally drop/recreate cml_db, alembic upgrade head, then import.

  1. Regenerate the six CSVs from the new workbook (overwrites scripts/seed_data/master_export/): 

    cd backend && uv run --with openpyxl python scripts/convert_master_export.py "path/to/Master Export.xlsx"
    If the export adds or moves columns (not just rows), the price parser offsets in scripts/import_master_export.py (_build_pricing) must be updated to match — that is a code change shipped with a normal deploy.

  2. Import against production (no schema drop), geocoding on: 

    railway status   # confirm production project + environment
PG_SERVICE=$(railway status --json | jq -r '[.environments.edges[].node.serviceInstances.edges[].node.serviceName]|unique|.[]' | grep -i '^postgres' | head -1)
export DATABASE_URL=$(railway variable list --service "$PG_SERVICE" --json | jq -r '.DATABASE_PUBLIC_URL')
cd backend && uv run python scripts/import_master_export.py --input-dir scripts/seed_data/master_export
    The script runs locally against prod over DATABASE_PUBLIC_URL, so run it on the branch carrying the new CSVs. Local equivalent: docker-compose exec backend python scripts/import_master_export.py --input-dir scripts/seed_data/master_export (add --no-geocode offline, --dry-run to roll back).

  3. Verify (example: confirm a new pricing key landed): 

    psql "$DATABASE_URL" -P pager=off -c "
SELECT count(*) AS cards,
  count(*) FILTER (WHERE EXISTS (SELECT 1 FROM jsonb_array_elements(pricing->'modifiers') m WHERE m->>'name'='Five or more storeys (BSA)')) AS has_bsa
FROM price_cards;"

⚠️ The import re-reads enrolled and referral_email from the export and overwrites both: a firm left blank in the export becomes un-enrolled (its Proceed/Callback buttons disappear), and any email-test containment (§3.1) is undone. Confirm those columns in the workbook before importing. Once the platform holds real data, take a pg_dump first.

3. Testing transactional email in production¶

Goal: confirm SparkPost delivers (and passes DKIM/SPF/DMARC) without emailing any real firm. Firm-facing mail fires only to organisations.referral_email, so containment is about controlling that one column. Record-level DNS setup: docs/dns-email-configuration.md.

Flows that send to referral_email: Proceed, Callback, enrolment invite. Password-reset mail goes to firm_users.email instead, so this containment doesn't affect it.

3.1 Contain the blast radius¶

UPDATE organisations SET referral_email = NULL;
UPDATE organisations SET referral_email = 'you@example.com'
  WHERE cml_firm_id = 'CML-002' AND enrolled = true;

-- verify: expect exactly ONE row
SELECT cml_firm_id, trading_name, enrolled, referral_email
FROM organisations WHERE referral_email IS NOT NULL;

If the second UPDATE matches 0 rows, every org ends up NULL and nothing sends — always run the verify SELECT.

3.2 Set the key and trigger a send¶

Set SPARKPOST_API_KEY in Railway (empty ⇒ mock mode, logs only; setting it triggers a redeploy). Confirm the running app sees it:

railway run python -c "from app.config import settings; print(bool(settings.sparkpost_api_key), settings.sparkpost_from_email)"

Then trigger one email: - Enrolment invite — simplest single send; use an un-enrolled org pointed at your inbox (invite-enrollment returns 409 for an enrolled org). - Proceed / Callback — the firm must rank into the top-5 contactable for a search first; run a search in the firm's locality, then Proceed/Callback it.

3.3 Confirm deliverability¶

Open the received mail; check headers show DKIM=pass, SPF=pass, DMARC=pass. Sender must be noreply@mail.choosemylawyer.ai or DMARC quarantines it. A brand-new sending domain has no reputation, so early mail may land in spam even when authentication passes. The audit BCC is added only when CML_AUDIT_EMAIL is set, and must be a deliverable mailbox — never the noreply@mail. address.

3.4 Walking the email workflow through time¶

The scheduled workflow cycle (outcome requests, contact checks, reminders, exceptions — see docs/email-spec.md) normally runs once a day at 09:00 and spans weeks of calendar time. To test it without waiting, run the cycle on demand "as of" a future date:

curl -s -X POST -H "X-Admin-Key: $ADMIN_API_KEY" \
  "$API_BASE/api/admin/email-cycle/run?as_of=2026-07-20"
# → {"as_of": "2026-07-20", "sent": {"firm_02": 1}}

Create a referral (Proceed/Callback, with containment per §3.1), then call the endpoint repeatedly with advancing dates — e.g. +3 working days (callback outcome request), then further ahead for the consumer contact check, reminder and exception. Each response lists what fired; every send also appears in the admin email log (/admin/email-log). Omitting as_of runs the cycle for today.

Walking many weeks at once (e.g. reaching the 10-week Firm-05 matter-progress email) is tedious by hand, so backend/scripts/walk_email_cycle.py automates it: it calls the endpoint once per simulated day, prints what each day sent, and waits for Enter after any day that sent emails ("press Enter to continue, Ctrl+C to stop") so the tokenised links in those emails can be exercised before time moves on. Stdlib-only — runs on the host, no container needed:

python3 backend/scripts/walk_email_cycle.py                     # local; today + 77 days (11 weeks)
python3 backend/scripts/walk_email_cycle.py --start 2026-07-13 --days 84

ADMIN_API_KEY=<prod-admin-key> python3 backend/scripts/walk_email_cycle.py \
  --base-url https://backend-production-2962.up.railway.app     # against production

railway run python3 backend/scripts/walk_email_cycle.py \
  --base-url https://backend-production-2962.up.railway.app     # against production, key from Railway

The admin key comes from the ADMIN_API_KEY environment variable, falling back to the repo-root .env (the local default). railway run injects ADMIN_API_KEY from the Railway environment, so no inline key is needed. Ctrl+C stops the walk, and re-running is safe (dedupe as above).

⚠️ Against production, future-dated walks are effectively irreversible: emails fire for real to whatever transactions are pending, and dedupe then suppresses the legitimate send when the real calendar date arrives. Only walk prod while the DB holds just test transactions (containment per §3.1).

Safe to repeat: sends are deduped per (transaction, template), so re-running a date — or the real 09:00 cycle running later — never double-sends. Due dates are computed from when the previous email was actually recorded, so a chain walked this way fires slightly sooner than the real calendar would — fine for testing, just don't mix time-travelled dates into transactions you care about operationally.

3.5 Previewing email templates without sending¶

Every automated template renders inside a shared branded shell (backend/app/services/email_shell.py, issue #162) — doctype, constrained width, branded header, bordered "card" treatment for the callback tracker / transaction summary / details blocks, and a signature block ("The CML Team" → CML logo → info@choosemylawyer.ai) appended to every send. To review the rendered output of every in-scope template with representative sample data, without sending anything or touching the database:

cd backend
uv run python scripts/preview_emails.py            # writes HTML + text to scripts/email_preview_output/
uv run python scripts/preview_emails.py --list     # list the registered keys only

Runs in the backend's uv environment (it imports the app package), but needs no running server and no Postgres — it only calls the render functions. Output is gitignored; open the .html files directly in a browser and the paired .txt files show the plain-text alternative that now accompanies every send. REGISTRY in that script is the single source of truth for "every template in scope" — backend/tests/unit/test_email_preview_registry.py asserts it exactly matches the templates defined in email.py / referral_emails.py / workflow_emails.py, so a template added without a matching registration fails that test rather than silently going unreviewed.

3.6 Restore before go-live ⚠️¶

SET referral_email = NULL wiped the seeded addresses. Re-running import_master_export.py repopulates referral_email and enrolled from the export — so any reseed/import undoes this containment. Restore real addresses before real firms are invited or sent leads.

4. Admin metrics dashboard¶

Hidden operations dashboard showing the consumer funnel, firm leaderboard and the chargeable-events ledger. It replaces the ad-hoc SQL approach for routine reporting (issue #74).

4.1 How to sign in¶

  1. Browse directly to https://<app-domain>/admin (locally: http://localhost:3000/admin). There are no links to it anywhere on the site, it is noindex, and it is disallowed in robots.txt — bookmark it.
  2. You'll see an "Admin sign in" card with a single Admin key field. Enter the value of the ADMIN_API_KEY environment variable (Railway → service → Variables in production; .env locally, default local-dev-admin-key). There is no username.
  3. A wrong key shows "Invalid admin key" and grants nothing. The correct key opens the dashboard.
  4. The key is held in sessionStorage for the browser tab only — closing the tab (or clicking Sign out, top right) forgets it, and you sign in again next time. If the key is rotated mid-session you'll be dropped back to the sign-in card on the next request.

The dashboard key is the admin API key — the same secret that protects every /api/admin/* endpoint (sent as the X-Admin-Key header). Rotating it in Railway signs everyone out and invalidates any scripts using the old key. ADMIN_API_KEY must be set in Railway before go-live — without it the dashboard cannot be accessed.

4.2 What it shows¶

Pick a period at the top — 7 / 30 / 90 days / All time (7/30 bucket the activity chart daily, 90/all weekly). Every section refetches for the selected period.

  • Stat tiles — page views, searches started, intakes completed, results viewed, selects, callback leads, interest registrations, pipeline value, average quote.
  • Funnel — sessions started → intakes completed → results viewed → converted, with conversion rates between stages.
  • Activity over time — sessions started vs selects + callback leads, zero-filled buckets.
  • Lead quality — callback contact rate, conflict-check outcomes, reviews received.
  • Marketing — Google Ads click-ID share of sessions and conversions (paid session share).
  • Firm leaderboard — every enrolled firm (including zero-lead firms) plus any non-enrolled firm with interest registrations (the recruitment pipeline), sorted by total leads.
  • Chargeable-events ledger — one row per Select/Callback lead: short unique ID (hover for the full ID), date, type, firm, client name + email, matter summary, quote, conflict-check outcome and contacted flag. This is the billing audit trail — each row corresponds 1:1 with the lead email the firm received, so use it to reconcile the periodic manual invoices.

4.3 Caveats when reading the numbers¶

  • Page-view and funnel event counts are consent-gated — visitors who decline marketing cookies are not counted, so those figures undercount. Leads, appointments and interest registrations come from durable tables and are exact.
  • Pipeline value counts each callback submission once, at the highest quoted price among the firms selected (a submission with no quotes contributes nothing); Selects contribute their own quote. The same definition drives the average-quote tile. On the firm leaderboard, every firm involved in a callback carries the submission's highest quote as that lead's pipeline value — not the firm's own quote — so leaderboard values are not additive across firms. The ledger still itemises each firm's own quote per row (the billing audit trail is unchanged). Pipeline value measures lead pipeline, not instructed work.
  • The API behind the dashboard is available for scripted export if needed: GET /api/admin/metrics/{summary|timeseries|firms|ledger} with the X-Admin-Key header, e.g. curl -H "X-Admin-Key: $ADMIN_API_KEY" "https://<api-domain>/api/admin/metrics/ledger?limit=500".

4.4 Voiding a live referral (issue #176)¶

A consumer can hold only one live Select (Proceed) at a time — while one is referred, instruction_accepted, pre_exchange or contracts_exchanged, the platform refuses a further Select for that consumer (same search or, cross-search, the same email address), even to the same firm again. That block normally releases itself once the firm reports it can't act / wasn't instructed, or the matter completes or aborts. Void is the escape hatch for the cases that don't self-resolve — a mis-Select, a duplicate instruction, or a firm that has simply gone quiet and needs the founder to intervene rather than waiting indefinitely.

  • When to use it: a consumer is stuck unable to Select another firm because an earlier Select is live but wrong (sent to the wrong firm, a genuine duplicate, or a firm that isn't responding and CML has decided to release the consumer rather than keep waiting on it). This also covers a conflict check recorded against an open matter: recording a conflict outcome always sends the consumer the "pick another solicitor" email with a link back to their results, but that link only leads somewhere usable when the referral was still referred at the time — a conflict recorded once the matter has moved on (instruction_accepted, pre_exchange, contracts_exchanged) leaves the Select block in place, so voiding is the remedy.
  • How: from the ledger row for the referral, POST /api/admin/appointments/{id}/void with a required free-text {"reason": "..."}. Only a live referral can be voided — one already in a released state (including an earlier void) is refused with a 409. The reason, actor (admin) and timestamp are recorded on the referral's audit trail, and its workflow_state becomes voided — a state distinct from every firm-reported outcome, so it's never mistaken for the firm having said it couldn't act.
  • Consequences — read before voiding:
  • Silent. No email is sent to the consumer or the firm. If either needs telling, that's a manual conversation, same as today.
  • Stops further automation for that referral — outcome chasers, contact checks, matter progress requests, reminders and the exception escalation to CML all stop; nothing else is triggered by the void itself.
  • Excluded from billing. A voided referral is dropped from the chargeable-events CSV export (GET /api/admin/metrics/ledger/export) — it still appears in the JSON ledger (with workflow_state: "voided") so the void is visible, just not counted as chargeable.
  • Does not touch the firm's chargeable status. Organisation.chargeable_since is set the first time any of a firm's instructions is accepted and is never unset — voiding a referral that had already reached instruction_accepted leaves the firm chargeable on its other work.
  • Releases the consumer to Select again immediately; it does not notify them to do so.

4.5 Pilot feedback (issue #119)¶

The "Help improve CML" button on the journey pages (/chat, /results/...) opens a short, anonymous feedback form (four star ratings, an optional comment, an optional contact opt-in). It is a fourth, distinct feedback surface — separate from the tokenised Consumer-05/10/11 emails and from firm reputation reviews — and is never shown to consumers or firms.

  • Where to read it: /admin/pilot-feedback (same X-Admin-Key sign-in as the rest of the dashboard). Filter by date, and Download CSV to export the currently filtered rows. It is read-only — there is no moderation, approval or reply control, by design.
  • Summary scores appear on the main dashboard (/admin), inside the Funnel section — average rating and response count per question for the selected period.
  • The API is also available for scripted export: GET /api/admin/pilot-feedback with the X-Admin-Key header (from/to/limit/offset params), e.g. curl -H "X-Admin-Key: $ADMIN_API_KEY" "https://<api-domain>/api/admin/pilot-feedback?limit=500".

Post-pilot anonymisation (D-5/A-12). Once follow-up contact is no longer reasonably required (the pilot has ended and there is nothing left to action from a submission), null the contact columns on pilot_feedback, leaving the ratings and comment intact:

UPDATE pilot_feedback SET contact_name = NULL, contact_email = NULL;

contact_consent is deliberately left alone here — the consent was genuinely given at the time, so nulling only the two detail columns is a more honest record than also resetting the flag that says consent was given.

There is no automated purge job for this — anonymisation is a deliberate one-off operator action, run once, when the founder decides follow-up is no longer needed. The retention matrix held outside the repo (§ referenced from the privacy policy) is the founder's to update; this section only documents how to carry out the action once that decision is made.

5. Local development environment¶

Guidance for keeping the local dev loop usable on the current development hardware (OrbStack is the only container runtime on this machine — Docker Desktop was removed). See issue #137 for the full investigation this section is drawn from.

5.1 OrbStack memory/CPU allocation¶

The host has 8GB RAM. OrbStack's own settings (menu bar icon → Settings → Resources) currently cap it at 4GB / 2 CPUs. Leave it there rather than raising it:

  • The backend suite is I/O-bound on Postgres, not CPU-bound (measured: ~155s of CPU time inside a 390s wall-clock run — see §5.3), so extra CPUs bought little.
  • Every GB given to OrbStack is a GB the host OS, IDE and browser don't have. This machine already runs under chronic swap pressure (§5.4); raising the container cap trades container-side speed for more host-side swapping, which tends to be a net loss on an 8GB machine.

If you do need to raise it temporarily (e.g. a one-off large import), drop it back to 4GB afterwards rather than leaving it raised.

5.2 Stopping containers during backend test runs¶

uv run pytest runs on the host, not in a container — it connects straight to Postgres on localhost:5432 (see DATABASE_URL in .env.example and backend/tests/conftest.py). That means:

  • db is the only container pytest needs. Keep it running.
  • frontend is never touched by a backend test run — stop it before a test session to free memory: docker compose stop frontend.
  • backend (the uvicorn --reload container) isn't used by pytest either, since tests import the app in-process. It's only needed if you're manually hitting the API (e.g. via curl or the frontend) at the same time. Stop it too if you're not: docker compose stop backend.

Bring everything back with docker compose up -d when you need the full stack again.

5.3 Backend suite baseline & re-measuring¶

Recorded baseline (2026-07-20, main @ c52a7f5, full 880-test suite, this machine):

Measurement Value

CPU consumed 149.3s user + 5.8s sys = 155s of 390s wall (~60% idle, waiting on Postgres)

Current figure after the #137 fixture work (2026-07-31, same machine) — this is the number to compare against, not the baseline above:

Measurement Value

Randomised order (--random-order) 889 tests, 50.37s, exit 0

To re-measure:

cd backend
docker compose stop frontend backend   # optional, per §5.2 — db must stay up
/usr/bin/time -l uv run pytest -q      # macOS BSD time: reports "real" wall time + CPU time

Paste the wall-clock time and the pytest summary line together. A regression shows up as wall time drifting up from ~49s with a comparable test count. The usual suspects are the two fixtures #137 addressed: a teardown that goes back to TRUNCATE, or an engine that loses its connection pool (backend/tests/conftest.py).

5.4 Hardware note (advisory)¶

The current development machine is a 2018 MacBook Pro, i5-8279U (quad-core), 8GB RAM, running chronically under swap pressure (recorded 2026-07-20: 3.9GB of 5GB swap in use, OrbStack capped at 4GB). This is below comfortable spec for a Postgres + FastAPI + Next.js + Docker stack, and it compounds the cost of everything else — see §5.1 and §5.3.

This is advisory only — nothing in the pipeline depends on it, and #137's remedy (targeted local runs, full suite in CI) makes the constraint tolerable rather than requiring an upgrade. If a hardware refresh is on the table anyway, the main lever is RAM: 16GB+ removes the swap pressure that currently taxes every container, IDE and browser tab at once; a newer CPU generation helps build/lint/typecheck times but is a smaller factor than RAM for this particular bottleneck.

6. Repository, CI gates & deployment wiring¶

6.1 Where the repository lives¶

The canonical remote is choose-my-lawyer/cml. It moved there from tomstagg/cml on 2026-08-03. If your local clone predates that, re-point it:

git remote set-url origin git@github.com:choose-my-lawyer/cml.git

⚠️ GitHub serves a permanent redirect from the old path, so a stale remote keeps fetching and pushing without any error. A clone can look healthy for weeks while pointing at the old name. Check with git remote -v rather than assuming.

The move was not cosmetic. Branch protection and rulesets are paywalled for private repositories on GitHub Free — both PUT /repos/{o}/{r}/branches/main/protection and GET /repos/{o}/{r}/rulesets return 403 "Upgrade to GitHub Pro or make this repository public". The choose-my-lawyer organisation is on the team plan, which lifts that restriction. A useful diagnostic: once the plan is sufficient, an unconfigured branch returns 404 "Branch not protected" instead of 403.

tomstagg/cml-docs (the GitHub Pages target in .github/workflows/docs-site.yml) deliberately stayed on the personal account. The external_repository: value in that workflow is correct as written and should not be changed to the organisation.

6.2 Branch protection on main¶

Setting Value
Required checks Backend Tests, Backend Lint, Frontend
strict (branch up to date before merge) true
Required approving reviews 0
enforce_admins false
Force pushes / branch deletion blocked

The three context strings must match the name: fields in .github/workflows/ci.yml exactly — they are the display names, not the job keys (test, lint, frontend). Rename a job's name: and its gate silently stops being required, because GitHub waits for a context that never reports.

Required approvals are 0 deliberately: the pilot is a single-maintainer repository, and the reviewer cannot approve agent-authored PRs. The gate here is green CI, not sign-off. enforce_admins: false means an admin can still merge past a stuck check — that is the escape hatch, not the intended path.

To re-apply after any change:

gh api -X PUT repos/choose-my-lawyer/cml/branches/main/protection \
  -H "Accept: application/vnd.github+json" --input - <<'JSON'
{
  "required_status_checks": { "strict": true,
    "contexts": ["Backend Tests", "Backend Lint", "Frontend"] },
  "enforce_admins": false,
  "required_pull_request_reviews": { "required_approving_review_count": 0 },
  "restrictions": null
}
JSON

⚠️ Use --input - with a JSON body, not -f flags. gh api -f sends every value as a string, so -f 'required_status_checks[strict]=true' submits "true" and -f 'restrictions=null' submits the literal string "null" — both rejected with a 422 that does not explain the cause.

6.3 Railway deployment wiring¶

Both application services deploy from this repository; Postgres runs from an image.

Service Source Root directory
backend choose-my-lawyer/cml @ main /backend
frontend choose-my-lawyer/cml @ main /frontend

Railway's access comes from the railway-app GitHub App installed on the organisation (repository_selection: all). That installation is what a repository transfer breaks: the App is installed per account, so it does not follow a repo to a new owner. After any future move, install the App on the destination account first, then re-point each service:

railway environment edit --service-config backend  source.repo "<owner>/cml"
railway environment edit --service-config frontend source.repo "<owner>/cml"

⚠️ Changing source.repo does not trigger a deployment. Railway builds on push webhooks; source.repo only records where the next build pulls from. After re-pointing, the service looks "stuck" on the old deployment when in fact nothing has happened to deploy. Before assuming breakage, compare git rev-parse origin/main against the running deployment's meta.commitHash (railway deployment list --service <svc> --json) — if they match, the service is in sync. This differs from deploy.* patches such as multiRegionConfig, which do redeploy on commit.

⚠️ railway redeploy does not prove repository access. It reuses the existing built image — the new deployment carries the same meta.imageDigest and inherits the previous deployment's meta.repo string, so it never contacts GitHub. It verifies that the service restarts and passes its healthcheck, nothing more. The only real test of the source path is a build triggered by a commit.

6.4 What survives a repository transfer¶

Recorded from the 2026-08-03 move, for whenever this is done again:

Item Outcome
Issues, PRs, branches, Actions run history move with the repo
Actions secrets (CML_DOCS_DEPLOY_KEY) survived — verify with gh secret list, do not assume
Railway GitHub App installation does not follow; reinstall on the new owner
Railway source.repo does not follow; patch each service
Project board (users/tomstagg/projects/4) unaffected — cards reference issues by node ID
Local origin remote keeps working via redirect; update it explicitly

⚠️ CML_DOCS_DEPLOY_KEY survived, but its private half exists nowhere else — not on disk, not in the repo, and GitHub secrets are write-only. If it is ever lost it can only be regenerated: new keypair, public half onto tomstagg/cml-docs deploy keys, private half back as the secret.

One organisation-level setting is worth checking after a move, because it is invisible from the repository: Org Settings → Actions → General must allow third-party actions, since CI uses astral-sh/setup-uv and the docs workflow uses peaceiris/actions-gh-pages. Reading it via the API needs the admin:org scope (gh auth refresh -h github.com -s admin:org); the repository-level gh api repos/choose-my-lawyer/cml/actions/permissions is a weaker but usually sufficient proxy.

7. Domains & DNS (apex → www)¶

www.choosemylawyer.ai is the canonical host (issue #68) and is hardcoded as such in app/layout.tsx, app/robots.ts and app/sitemap.ts.

7.1 Current state¶

Name Record Points at
choosemylawyer.ai (apex) A 15.197.225.128, 3.33.251.168 GoDaddy domain forwarding
www.choosemylawyer.ai CNAME eqofjh7n.up.railway.app (Railway frontend)

Nameservers are GoDaddy (ns01/ns02.domaincontrol.com).

GoDaddy's forwarding redirects the root path only and strips everything else, so every deep apex URL 404s — choosemylawyer.ai/conveyancing, /robots.txt, /sitemap.xml. Inbound links using the apex form dead-end and pass no link equity.

7.2 The application side (issue #146)¶

frontend/middleware.ts 308-redirects any apex request to the same path and query on www. It keys off host (Railway's proxy forwards the original custom domain in it), falling back to x-forwarded-host only when host is absent — trusting a client-supplied header first could silently disable the redirect in production.

It only takes effect once the apex actually resolves to the Railway frontend service. Until the DNS below changes, the middleware never sees the request and the 404s persist.

7.3 Operator steps — pointing the apex at Railway¶

⚠️ There is no "keep DNS at GoDaddy" option. Railway issues a CNAME (plus a verification TXT) for a root domain and never A records, and GoDaddy supports neither CNAME flattening nor dynamic ALIAS — Railway lists it by name among the providers that don't. So pointing the apex at Railway requires moving the whole zone to a provider that does (step 2). Budget for a DNS migration including email, not a two-record edit.

Step 1 — add the domain in Railway. Dashboard → cml project → frontend service → Settings → Networking → Custom Domain → add choosemylawyer.ai, or:

railway domain choosemylawyer.ai --service frontend

Railway returns both records, and both are required — the CNAME alone leaves the certificate stuck on VALIDATING_OWNERSHIP:

Host Type Value
@ CNAME 88ujwzag.up.railway.app
_railway-verify TXT railway-verify=<verification-token>

Re-read them with railway domain status <id> rather than trusting the pair above: removing and re-adding the domain mints a fresh target and token.

Step 2 — move DNS to a provider with apex CNAME flattening (e.g. Cloudflare).

⚠️ This moves all DNS for the domain, including email. Getting it wrong breaks inbound mail and outbound deliverability — including the transactional email hardened in issue #155. Migrate every record below before changing nameservers, then verify.

Records that must be carried across (captured 03.08.26 — re-enumerate the live zone before migrating, see §7.5; do not trust this table as current):

Host Type Value Breaks if dropped
@ MX 0 choosemylawyer-ai.mail.protection.outlook.com Inbound mail
@ TXT v=spf1 include:spf.protection.outlook.com -all Outbound deliverability
@ TXT v=verifydomain MS=2346795 M365 domain ownership
@ TXT google-site-verification=gfIZcDCO_n0H3hbVWZ-N9j5Ld_B_4GiaUy86PTlENdw Search Console
_dmarc TXT v=DMARC1; p=quarantine; adkim=r; aspf=r; rua=mailto:<dmarc-rua-mailbox>; DMARC enforcement
www CNAME eqofjh7n.up.railway.app The site
api CNAME 3yknhbp0.up.railway.app The site — the frontend calls this host (it is in the CSP connect-src)
mail CNAME sparkpostmail.com All transactional email
autodiscover CNAME autodiscover.outlook.com Outlook / mobile mail-client setup

_domainconnect is GoDaddy-specific and is not carried across.

api is easy to overlook because nothing about the domain move suggests it, but it is the production backend — dropping it takes the whole site down, not just email.

SparkPost needs only the single mail CNAME. Do not hand-copy DKIM TXT records under mail.: it is a bare CNAME to sparkpostmail.com, and SPF, DKIM and bounce all resolve through it (scph*._domainkey.mail.choosemylawyer.ai does not exist in this zone). A TXT record cannot coexist with a CNAME at the same name. After the move, re-verify the sending and bounce domains in the SparkPost console rather than reconstructing records by hand.

Then add both step-1 records at the new provider: @ as a CNAME to the Railway target (relying on the provider's flattening) and the _railway-verify TXT. On Cloudflare, set the apex CNAME to DNS only (grey cloud) — proxying it terminates TLS at Cloudflare and Railway's certificate never validates.

The GoDaddy apex forwarding needs no separate step: it is the two apex A records in GoDaddy's zone (§7.1) and only functions while GoDaddy is authoritative, so moving the nameservers retires it. Tidy it up in My Products → Domains → choosemylawyer.ai → Forwarding afterwards, but it cannot override Cloudflare. (Were the zone ever moved back to GoDaddy, it would need deleting explicitly — it is what strips the path today.)

Then wait for Railway to show the apex certificate as Issued.

Expected: every line a 301/308 to the same path and query on https://www.choosemylawyer.ai. Then confirm www still serves directly (curl -s -o /dev/null -w "%{http_code}" https://www.choosemylawyer.ai/conveyancing → 200).

If step 2B was taken, also verify email before considering the change done: send a test through §3, confirm it arrives, and check the SparkPost console still reports the sending domain and bounce domain as verified.

7.5 Re-enumerating the zone before a migration¶

The table in §7.3 is a snapshot, and a migration checklist that is nearly right is worse than none — it reads as authoritative. Enumerate the live zone yourself first:

for h in @ www api mail autodiscover admin app staging cdn blog webmail smtp \
         lyncdiscover sip msoid enterpriseregistration enterpriseenrollment \
         selector1._domainkey selector2._domainkey _dmarc _domainconnect; do
  n=$([ "$h" = "@" ] && echo choosemylawyer.ai || echo "$h.choosemylawyer.ai")
  v=$(dig +short CNAME "$n"; dig +short A "$n"; dig +short MX "$n"; dig +short TXT "$n")
  [ -n "$v" ] && printf "%-34s %s\n" "$h" "$(echo $v | tr '\n' ' ')"
done

Anything that answers and is not GoDaddy-specific has to exist at the new provider before the nameservers change. Note that records resolving through a CNAME (SparkPost's SPF/DKIM under mail.) belong to the target zone, not ours — carry the CNAME, not its answers.

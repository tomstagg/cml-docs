CML System Design (as-built)¶

The consolidated technical design record for Choose My Lawyer (CML). This describes the system as it is actually built — derived from the code, not from older plans. Where the running code diverges from the functional spec (requirements.md, incl. Annex One) or from older docs, the divergence is called out explicitly.

Document roles - This file — architecture, data model, engines, integrations (the "how it works" reference). - docs/admin-guide.md — operations runbook (enrolment, reseeds, email testing). - docs/requirements.md (Annex One) — canonical functional spec + the source-of-truth numbers for ranking/pricing. Where a constant matters, this doc states the as-built value and points to the Annex One section; it does not silently re-author Annex One. - ITERATIONS.md — forward-looking backlog (not covered here).

MVP scope: residential conveyancing only · West Midlands Combined Authority (WMCA) · firms manually enrolled and priced · ~90-day PPC-driven pilot. Goal is commercial validation.

1. Overview¶

Consumers complete a short pathway-aware intake (Buying / Selling / Both) and receive a ranked list of solicitors with a calculated Total Effective Price. The full in-scope WMCA market is ranked; the top-5 contactable (enrolled, active) firms get Proceed / Request a callback actions. Firm data — identity, pricing, and pre-computed reputation/complaints/regulatory scores — is curated in the Master Export workbook and loaded by a single importer.

2. Architecture & topology¶

Browser ──► Next.js 15 (App Router)  ──► FastAPI (async)  ──► PostgreSQL 16
                 frontend/                   backend/             Railway PG
                 :3000                        :8000               :5432
  • Frontend proxies /api/* to the backend via next.config.ts rewrites.
  • Backend: async SQLAlchemy + asyncpg.
  • APScheduler runs in-process with FastAPI (no separate worker/queue) — wired into the lifespan in app/main.py via app/tasks/scheduler.py.
  • Hosting: two Railway services (backend, frontend) from their Dockerfiles + a managed Postgres add-on. Local dev via docker-compose.

Address lookup proxy (app/api/public/address_lookup.py, #124/#127): GET /api/public/address-lookup/{postcode} returns {"available": bool, "addresses": […]} for the Select/Callback journey forms — a premise shortlist that auto-fills the address lines, with a manual-entry escape hatch (components/journey/AddressFields.tsx). Proxies Ideal Postcodes (api.ideal-postcodes.co.uk/v1/postcodes/{postcode}; #127 replaced the original provider, which ceased operating in February 2026) so the API key (ADDRESS_LOOKUP_API_KEY) stays server-side. Rate-limited 30/min per IP; never surfaces a 5xx — no key, an implausible postcode shape, a timeout, a non-2xx (including postcode-not-found, whose "did you mean" suggestions are ignored, #127 D-3) or a malformed body all degrade to {"available": false, "addresses": []} and the form falls back to manual entry. First results page only (#127 D-5); spend protection is dashboard-side (#127 D-4). Distinct from the postcodes.io validity tick and geocoding, which are free and keyless.

5. Data model & data catalogue¶

Engine: PostgreSQL 16, UUID primary keys, async asyncpg driver. Schema is a single Alembic file backend/alembic/versions/0001_initial_schema.py (pre-launch policy: edit 0001 in place + drop/recreate; no new revisions until go-live). {
  "freehold":  { "purchase": {"150000": 950, ... "1500000": 1450}, "sale": { ... } },
  "leasehold": { "purchase": { ... }, "sale": { ... } },     // 7 anchors each: 150k,250k,500k,750k,1m,1.25m,1.5m

}

Sentinel Price-tab cells (Unavailable / Not Offered / Withheld) are recorded in anchor_states per tenure/side rather than as a numeric fee; the anchor lookup then has no fee for that cell.

Every named modifiers/additional_costs row on the current (07.07.26) Master Export is imported verbatim, whether or not price_calc.py currently applies it — see §6 for which rows are wired into a trigger.

6. Pricing engine (as-built)¶

Deterministic, rules-based, no runtime AI. Implementation: backend/app/services/price_calc.py. Spec: Annex One §6/§10 for the formula and confidence factors; the Canonical Pricing Specification (CPS) for pricing item definitions, trigger conditions, consumer question copy and Price Item display names. Breakdown lines are labelled with the CPS Price Item names via the single CPS_DISPLAY_NAMES map (raw Master Export column string → display name).

Constants (as-built)¶

Constant Code value Notes
CONFIDENCE_UPLIFT_C 0.20 Estimated legal-fee uplift (Annex One §10); set by engine-tweaks.md.
CONFIDENCE_UPLIFT_D 0.02 Per-item estimated-disbursement uplift (§6)
VAT_RATE 0.20 On legal fees only (not on HMLR / VAT-free searches)
ANCHORS 150k, 250k, 500k, 750k, 1m, 1.25m, 1.5m Seven CML anchor points

Formula¶

P_estimated       = anchor_fee + Σ applicable modifiers + Σ applicable additional costs
P_legal_effective = P_estimated × (1 + 0.20)   if price_type = estimated
                  = P_estimated                if price_type = verified
P_effective       = P_legal_effective + (P_legal_effective × 0.20 VAT) + Σ included disbursements
  • Anchor lookup (_nearest_anchor): the user's property value snaps to the closest of the seven anchors by absolute distance (nearest, not round-up).
  • Modifiers applied (purchase): new-build (freehold), new-lease (leasehold), acting-for-lender (when mortgage), shared ownership / HTB equity loan / HTB ISA (three independent CPS split flags), gifted deposit, unregistered-title purchase, Building Safety Act / Higher-Risk Building (leasehold AND answer Yes), Solar Panels (answer Yes), Freehold Management Company (freehold AND answer Yes), Existing Tenancy (checkbox true). (Sale): unregistered-title sale, additional mortgage redemption (modifier × (n − 1) for mortgage_redemption_count n > 1 — the first redemption is in the base fee), BSA (leasehold AND Yes), Solar Panels (answer Yes), Help to Buy Redemption (checkbox true). Unregistered-title fires on a No answer to the registered-title question; a Don't know answer never applies a modifier. Zero-amount lines are dropped from display. "Leasehold supplement" is imported onto every card but deliberately never applied by any trigger — the LHP/LHS anchor grids already carry the leasehold premium for most firms, so applying it again would double-count; revisit pending founder confirmation.
  • Additional costs applied: Identity Verification (firm amount × party count, "Four or more" = ×4, charged once per transaction — purchase side on combined), onboarding, transfer-admin (both sides), file storage (wherever the firm records one; never user-gated); SDLT admin (purchase).
  • Disbursements (purchase side only): the CML standard search pack — honouring its per-item estimated (+2% d) and vat_applies flags — plus the HM Land Registry Scale 1 (online) registration fee (a known, VAT-free, non-estimated public fee: ≤£80k→£20, ≤£100k→£40, ≤£200k→£100, ≤£500k→£150, ≤£1m→£295, >£1m→£500). The CPS HMLR sale-side fee is not implemented (calculation undefined in the CPS).
  • Breakdown grouping: quote lines are returned in three lists matching the CPS categories — adjustments (legal-fee modifiers), additional_costs, disbursements.
  • Combined buy+sell: the pricer runs once per side and sums the two totals (both sides carry their own VAT; disbursements arise on the purchase side only).
  • A firm with no anchors for the tenure/side, an unpriceable intake, or price_type = no_data returns no quote and is dropped from results.

Pending CPS updates: the "Don't know" pricing consequence beyond "never apply the modifier" still awaits a CPS update (issue #55; the Solar Panels, Freehold Management Company, Existing Tenancy and Help to Buy Redemption modifiers are priced as of the 07.07.26 Master Export).

7. Ranking engine (as-built)¶

Deterministic six-factor scorecard. Identical inputs always produce identical outputs. Implementation: ranking.py (factor scorers), scorecard.py (weights + tie-break), search.py (orchestration). Spec: Annex One §5–§16.

Factor scoring¶

Factor Input Basis
Reputation organisations.adjusted_reputation_value Relative min–max across the result set (all-equal ⇒ 50)
Price Total Effective Price (§6) Relative inverse min–max — lower price scores higher (all-equal ⇒ 50)
Complaints complaints_summary.score Absolute, consumed directly (missing ⇒ 100)
Regulatory regulatory_summary.score Absolute, consumed directly (missing ⇒ 100)
Distance nearest office (haversine, miles) Banded: 0–2→100, 2–5→95, 5–10→85, 10–15→70, 15–25→50, 25–40→25, 40+→10
Offices office count Banded: 1→70, 2–3→78, 4–6→85, 7–10→90, 11–20→95, 21+→100

Distance is banded by miles, not min–max normalised (changed per engine-tweaks.md). Bands are lower-bound-inclusive top-down (exactly 2.0mi → 95).

Scorecards (scorecard.py::SCORECARDS, integer weights summing to 100)¶

Variant Rep Price Compl Reg Dist Off
balanced 27 23 15 15 10 10
reputation 40 20 12 12 8 8
price 20 40 12 12 8 8
complaints 18 18 40 10 7 7
regulatory 18 18 10 40 7 7
distance 17 17 10 10 40 6
offices 17 17 10 10 6 40

The user picks one priority factor on the chat preference step (default balanced).

  • Distance excluded (no postcode, or include_distance=false, or a postcode that fails to geocode): distance weight → 0 and the remaining weights are proportionately rescaled to sum to 100 (Annex One §8.2). When a postcode fails to geocode, the consumer is told why via distance_status (postcode_not_found / geocoding_unavailable) and offered an inline re-entry / retry on the results page (issue #182, D-1).
  • Overall score = Σ(factor × weight) / 100.
  • Tie-break order (§11): overall → reputation → complaints → regulatory → price → distance score → offices → alphabetical by firm name.

Sequencing & eligibility (search.py)¶

  1. Eligibility filter (upstream of scoring): exclude organisations.excluded = true. Firms without a usable price card (no card, price_type = no_data, or an intake that cannot be priced) are included but ranked after all priceable firms with quote = null and factor_scores.price = null (§8.13). They are not eligible for the top-5 contactable set.
  2. Rank the entire in-scope WMCA market with the chosen scorecard.
  3. Extract the top 5 contactable from that ordering: enrolled = true AND active_in_pilot = true, first five in rank order. Firms ranked 6+ (or not contactable) are shown without Proceed/ Callback actions. This preserves the "whole of market / independent" positioning.

No per-CTA gating. Proceed/Callback availability is driven solely by enrolled + active_in_pilot + top-5 membership (results) and an enrolled check (submit endpoints). There is no per-firm "Proceed enabled" / "Callback enabled" switch — the earlier vestigial proceed_enabled / callback_enabled columns were removed. Per-CTA control would need wiring into search.py and the appointment endpoints.

8. Google lead generation (Google Ads click-ID attribution)¶

PPC (Google Ads) is the pilot's traffic source. CML captures the ad click ID on landing, ties it to the lead it produces, and can hand that back to the agency for an offline "Import conversions from clicks" upload. There is no server-side conversion postback, no gtag/GA4, and no UTM parsing — attribution is purely on the Google click ID, exported and uploaded out-of-band.

What is captured¶

Parameter When Google uses it
gclid Standard Google Ads click ID (the common case)
gbraid iOS traffic, app→web journeys
wbraid iOS traffic, web→web journeys

Whichever is present in the landing URL is read verbatim (e.g. https://choosemylawyer.ai/?gclid=…). Capture is site-wide — the ad's final URL can point at any page. UTM params are not captured.

Where it is stored (three stages — frontend/lib/clickIds.ts → DB)¶

  1. Browser, on landing — <ClickIdCapture /> (mounted in the root layout) writes any present click ID to a first-party cookie (sozo_gclid / sozo_gbraid / sozo_wbraid, 90-day max-age) with a localStorage mirror. Capture is unconditional — NOT gated by cookie consent (so attribution survives a declined banner), and only writes when a param is present (inert for organic/direct). The Meta Pixel / analytics tracking in §9 is consent-gated; this is the deliberate exception.
  2. Chat session, on intake start — stamped onto chat_sessions.{gclid,gbraid,wbraid}; the session created_at is the landing-stage capture time.
  3. Lead, on conversion — at Proceed/Callback the current click ID is read again and stamped onto appointments.{gclid,gbraid,wbraid} plus click_captured_at (conversion time), alongside the firm and quoted_price (conversion value). Storing at both stages lets attribution survive if one stage missed it.

A Proceed is one lead (appointments.type = select); a Callback to up to three firms produces one lead row per firm, all sharing the same click ID and click_captured_at.

Lead export for the agency¶

The click-ID data is captured on every session and lead, but there is no self-serve "download leads CSV" yet — for the pilot the export is produced on request from the production DB with the query below.

Attribution rules (decided 2026-07, issue #53):

  1. One conversion per user submission, not per firm. A callback to up to three firms is a single user action on one ad click, so it uploads as one CML Callback conversion (the DB still holds one appointments row per firm — the grouping happens at export). A Proceed is one conversion as before. Per-firm rows would triple-count callback clicks in Google Ads.
  2. conversion_value = highest quoted_price in the submission (MAX). The consumer transacts with at most one firm, so the value a click can realise is a single quote, not the sum of the bundle; summing would inflate callbacks ~3× relative to Proceeds and bias bidding towards the less-committed action. For Proceeds (single row) this degenerates to the row's own quote, keeping the two conversion actions directly comparable.
  3. conversion_time is emitted as yyyy-mm-dd HH:mm:ss+HH:mm in UTC (offset +00:00), one of Google's accepted click-import formats — no timezone ambiguity at upload.

The rules are interdependent: per-submission grouping (1) forces an aggregate value rule (2) and a single timestamp per row (3). Do not change one without revisiting the others.

SELECT
    a.session_id                      AS session_id,
    a.type                            AS lead_type,         -- 'select' (Proceed) or 'callback'
    CASE a.type WHEN 'select' THEN 'CML Proceed'
                WHEN 'callback' THEN 'CML Callback' END     AS conversion_name,
    COALESCE(a.gclid,  s.gclid)       AS gclid,             -- conversion-time value, else landing value
    COALESCE(a.gbraid, s.gbraid)      AS gbraid,
    COALESCE(a.wbraid, s.wbraid)      AS wbraid,
    to_char(MIN(COALESCE(a.click_captured_at, a.created_at)) AT TIME ZONE 'UTC',
            'YYYY-MM-DD HH24:MI:SS') || '+00:00'            AS conversion_time,
    MAX(a.quoted_price)               AS conversion_value,  -- GBP; highest quote in the submission
    'GBP'                             AS conversion_currency,
    COUNT(*)                          AS firms_contacted,   -- 1 for Proceed, 1–3 for Callback
    string_agg(o.cml_firm_id, '; ' ORDER BY o.cml_firm_id)  AS firm_ids,
    string_agg(a.id::text,    '; ' ORDER BY o.cml_firm_id)  AS lead_ids,
    s.created_at                      AS session_started_at -- landing-stage capture time
FROM appointments a
LEFT JOIN chat_sessions s ON s.id = a.session_id
JOIN organisations  o ON o.id = a.org_id
WHERE a.created_at >= :from_date AND a.created_at < :to_date   -- half-open range
GROUP BY a.session_id, a.type, a.click_captured_at,
         COALESCE(a.gclid,  s.gclid),
         COALESCE(a.gbraid, s.gbraid),
         COALESCE(a.wbraid, s.wbraid),
         s.created_at
ORDER BY conversion_time;
-- Google-attributable rows only: add
--   AND COALESCE(a.gclid,a.gbraid,a.wbraid,s.gclid,s.gbraid,s.wbraid) IS NOT NULL

Grouping grain caveats: a.click_captured_at is in the key because it is stamped once per submission (shared by every row of a callback bundle, distinct for a later Proceed in the same session). Since issue #176, only one Select can be live on a session (or consumer email) at a time — a second Proceed attempted while the first is still live is refused before an appointment is even created, so it never reaches this export. A second Proceed genuinely submitted later, once the first referral has been released (unable_to_act, not_instructed, completed, aborted or an admin void), is a distinct submission with its own click_captured_at, so the grouping grain still keeps the two apart rather than merging them. Rows whose session_id was nulled by a session deletion (ON DELETE SET NULL) group only by click ID and submission time; with no click ID at all they are excluded by the attributable-rows filter above, which is the only variant uploaded to Google.

The columns Google requires for the click-import are the click ID, conversion_name, conversion_time, conversion_value, conversion_currency; the rest (session_id, lead_type, firms_contacted, firm_ids, lead_ids, session_started_at) are for CML/agency reconciliation only.

Importing into Google Ads (agency)¶

Standard offline conversion import keyed on click ID (Goals → Conversions → New → Import → "Conversions from clicks"): - Create one conversion action per CML action — CML Proceed, CML Callback. - Multi-firm callbacks are already de-duplicated by the export (one row per submission — see the attribution rules in §8.3). As belt-and-braces, still set CML Callback to count "One" per click in the conversion-action settings. - Conversion time is emitted by the export as yyyy-mm-dd HH:mm:ss+00:00 (UTC offset included), which Google accepts directly — no account-timezone reconciliation needed. - Click-ID match window is ~90 days (Google-side); CML's 90-day cookie retention is aligned, but very delayed conversions may fall outside Google's window.

Privacy position¶

The click-ID cookie is first-party and holds only the opaque Google identifier — no name/email/phone. Personal details are captured separately at conversion under explicit data-sharing consent and are not part of the Google Ads feed (click ID + conversion metadata only). Meta Pixel / funnel analytics (§9) are consent-gated and independent of this attribution.

Google ad click ─ ?gclid=… ─► Landing: click ID → first-party cookie (90d, no consent gate)
        └─► Intake started → stamped on chat_session
              └─► Proceed / Callback → stamped on lead (+ click_captured_at, firm, quoted_price)
                    └─► Export (click ID · conversion name · time · GBP value) → Google Ads click import

Reputation now arrives pre-baked in the Master Export (adjusted_reputation_value), so the weekly Google Places sync was removed (see app/tasks/scheduler.py). GOOGLE_PLACES_API_KEY and the reviews.external_id / reviews.synced_at columns (the sync's idempotency/audit fields) have now been removed too. Scheduler cycle¶

One idempotent pass (app/services/email_cycle.py::run_email_cycle), run daily at 09:00 Europe/London by the in-process APScheduler (app/tasks/scheduler.py). Send retry, failure classification and alerting (issue #155)¶

send_email (app/services/email.py) covers every send in this section, including the standalone sends above — one implementation rather than a referral-only fix, so a dropped password reset or firm invitation gets the same handling as a dropped referral (D-5). It returns a SendResult (ok/reason/permanent/attempts) rather than a bare bool; existing if not ok: call sites keep working because SendResult.__bool__ mirrors ok.

Classification (_classify_failure): a SparkPost 4xx response (other than 429) is permanent; 5xx, 429, requests timeout/connection errors, and anything unclassifiable are transient. A transmission the API accepts with zero accepted recipients is also treated as permanent — the address was rejected without raising.

In-process retry: a transient failure is retried within the same send_email call, up to MAX_SEND_ATTEMPTS (3) attempts total, sleeping RETRY_BACKOFF_SECONDS ([10, 20], ~30s total) between them. Only the final attempt's outcome is written to email_events — a send that recovers leaves no failed row and raises no alert. Because a single call can block for up to ~30s, no caller may await send_email (or a wrapper of it) synchronously from a request handler: every send — referrals (app/api/public/callbacks.py, app/api/public/appointments.py), conflict-check (app/api/admin/appointments.py), enrollment/user invitation and password reset (app/api/admin/organisations.py, app/api/firm/auth.py) and session-save (app/api/public/sessions.py) — runs via BackgroundTasks, off the request path. The four standalone senders that used to take the request's own DB session (send_enrollment_invitation, send_user_invitation, send_password_reset_email, send_session_save_email) now open and commit a short-lived session of their own instead, matching send_conflict_check_failed.

Permanent-failure alerting (_alert_permanent_failure, in email.py so it covers every send): fires immediately, once, via a bare send_email call — never through _send_and_log — so the alert itself cannot be classified and recursively re-alerted. The alert email identifies the recipient, template, transaction id (where there is one), firm/consumer context, failure reason and attempts.

Durable sweep (app/services/email_cycle.py, called from run_email_cycle): _retry_outcome_and_review_due re-invokes send_outcome_email/send_review_email for a transient failure whose template (Consumer-03/04/05/06/09/10/11) has no daily due-scan of its own, and _retry_referral_due does the same for the referral/confirmation templates (Firm-01/03, Consumer-01/07 — referral_emails.py), re-rendering from the stored Appointment + ChatSession via the same _callback_context/_firm_referral/_submission_data helpers dispatch_callback_emails / dispatch_select_emails use (Consumer-01 reconstructs every sibling firm in the submission, not just the one appointment the failed row happens to be keyed to; Firm-03 preserves the original send date in its "call by"/"pack by" copy, not the retry's own clock). Every other retriable template is already re-attempted naturally each time its own "due" gate re-runs should_attempt. should_attempt (workflow_emails.py) allows at most one attempt per London calendar day, only while the pair's first attempt is within RETRY_WINDOW (2 days) of now, and never for a permanent failure.

_retry_exhaustion_due then scans the log directly (not a "due" condition, so it also catches a send whose business trigger went moot before the window expired) for every failed transient send past RETRY_WINDOW — not only the templates the sweep above can reconstruct: whether a send is retriable never gates whether it is alerted. Appointment-scoped sends are deduped per (appointment_id, template) pair; the appointment-less standalone sends in email.py (password reset, contact form, session save, enrollment/user invitation, conflict-check) have nothing that ever retries them, so each failed row is its own complete attempt history, deduped by the row's own id. Either way CML gets one exception email via _send_retry_exhausted_alert, deduped by a marker row — keyed exp_<template> (appointment-scoped) or exp_<event id> (appointment-less), truncated to the template column's String(32). A prefix (exp_) rather than the original suffix scheme (template + "_exp", e.g. firm_02_exp): a suffix sits inside the consumer_*/firm_* prefixes /admin/email-log's template filter matches on and appeared as a pseudo-send. The marker is written unconditionally regardless of the alert's own outcome, so a failed alert send cannot trigger a re-alert next cycle — but it records that outcome truthfully (sent or failed, with the alert's own failure reason), and dedup is "does any row exist for this marker" rather than "does a sent row exist", so a truthful failed marker does not reopen the door to re-alerting. Both exhaustion scans exclude marker rows themselves (exp_%), so a failed marker is never picked up as a fresh candidate by a later pass.

already_attempted (workflow_emails.py) now counts only sent rows (issue #155 D-3) — previously a failed row also counted as "attempted", which was silently blocking retry of every workflow email that had ever failed once. Its remaining caller (workflow_emails.py:1118, suppressing a second Consumer-05 on the same submission) and the exhaustion-marker dedup above are the only sites where "did this genuinely succeed" is the right question; every retry/gating site uses should_attempt.

Email-event log & admin visibility¶

Every send writes one email_events row (recipient, template key, transaction id, API-level sent/failed — no delivery webhooks). A failed row also carries failure_reason (provider message, truncated to FAILURE_REASON_MAX_LENGTH/500 chars so a long message can't fail the write) and failure_classification (transient/permanent) — added by Alembic 0002, additive and nullable, so pre-0002 failed rows keep both columns NULL. GET /api/admin/email-log (X-Admin-Key) serves it paginated with filters (transaction, firm, template prefix, date range) and now includes the failure reason; the admin UI at /admin/email-log displays it and visually distinguishes failed rows from sent ones (no resend control — manual intervention only, D-10).

Operational gotchas (lessons learned)¶

  1. NEXT_PUBLIC_* are build-time — set as Railway build variables; runtime-only env yields undefined in the browser bundle.
  2. Railway injects PORT — use ${PORT:-8000} in the backend CMD.
  3. DB URL protocol — Railway gives postgresql://; asyncpg needs postgresql+asyncpg:// (handled by config.py).
  4. Pre-launch schema policy — 0001_initial_schema.py is edited in place; an in-place edit no-ops on an already-migrated DB, so schema changes require a wipe-and-reseed (often surfacing as a 500 that looks like CORS). See docs/admin-guide.md.
  5. .env changes need docker-compose up -d (recreate), not restart.
  6. CORS must include both the Railway subdomain and the custom domain during cutover.
